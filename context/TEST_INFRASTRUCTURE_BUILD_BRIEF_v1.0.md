## Problem
Sessions stall mid-task because `test-verified-builds` / `ridgeco-validate` need a live `WORKER_SECRET` to run smoke tests, and the only way to get one into a session today is Brett pasting it — which the house convention already flags for rotation every time it happens. Separately, there's no dedicated test vendor/owner/tenant/property, so any real test risks touching a real record, and no guarantee a test SMS/email doesn't reach a real person.

## Goals
1. Any session can run read/write smoke tests against the Hub without ever holding `WORKER_SECRET`.
2. Testing is structurally confined to `maintenance-hub-staging` + dedicated `TEST-` records — never real data, by construction, not by discipline alone.
3. No notification generated by testing ever reaches a real vendor/owner/tenant. A real send that needs verifying goes only to Brett's own phone/email.

## Non-goals
- Not touching `WORKER_SECRET` itself, its rotation, or anything on production `maintenance-hub`'s auth gate.
- Not building general read/write access to the Hub for arbitrary session use — test/staging-scoped only.
- Not building the Rung-2 auto-ship path — this closes the Rung-1 "prepare" verification gap only.

## Design

### 1. New scoped Hub token: `HUB_TEST_TOKEN`
Follows the exact pattern already established by `OPS_QUEUE_TOKEN` / `CONTACTS_SYNC_TOKEN` / `SELFTEST_TOKEN`: a brand-new, independent env var, inert until set, checked in `worker.js` before falling through to `WORKER_SECRET`, allow-listing only test-safe paths. Set **only** as a secret on `maintenance-hub-staging` — never on production `maintenance-hub`. Even if this token leaked, it cannot reach real data, because the env var doesn't exist on prod at all.

**Allow-listed (read):** `GET /health, /vendors, /owners, /tenants, /properties, /workorders (+ /:id), /vendor-bills, /invoices` — same shape `test-verified-builds` already checks.

**Allow-listed (write)** — restricted further at the handler level, not just the route level: accepted only when every record ID touched (vendor/owner/tenant/property/new-WO assignment) resolves to a row flagged `Test:TRUE`. A request that would touch a non-test record is rejected with 403 regardless of path — belt-and-suspenders beyond the route allow-list.

**Never allow-listed under this token:** anything QB/payment/invoice-send, `/admin/*` except the seed endpoint below, `/config` global writes, auth/role endpoints.

### 2. Delivery: extend `gh-broker`, don't stand up a new Worker
Recommendation: add 2–3 tools to the existing `gh-broker` Worker/connector rather than a second Worker + second Cowork connector. `gh-broker` is already deployed, already connected in Cowork's connector settings, and already built to exactly this spec (holds a secret server-side, forwards it, never exposes it to a session). Extending it means the only manual step is setting two Cloudflare secrets — no new Worker, no new GitHub→Workers-Build connection, no new connector to add.

New `gh-broker` secrets: `HUB_TEST_TOKEN` (must match the value set on `maintenance-hub-staging`) and `HUB_STAGING_URL` (plain var).
New `gh-broker` tools: `hub_test_get(path)`, `hub_test_post(path, body)` — forward to `HUB_STAGING_URL` with `X-Auth-Token: HUB_TEST_TOKEN`, allow-list enforced client-side too as a second layer — plus `hub_test_seed()` (below).

If Brett would rather keep this fully separate from GitHub-repo access for blast-radius/audit reasons, a standalone Worker is the alternative — flagged as an open question below.

### 3. Dedicated test fixtures
New Hub endpoint `POST /admin/seed-test-fixtures`, gated by `HUB_TEST_TOKEN`, hard-blocked unless `isStaging`, idempotent (checks for existing `TEST-` rows before creating). Creates:
- `TEST-PROPERTY-001`
- `TEST-OWNER-001` (contact email/phone = Brett's own)
- `TEST-VENDOR-001` (contact phone = Brett's own)
- `TEST-TENANT-001` (contact phone = Brett's own)
- `TEST-WO-001` tying them together, so a full work-order lifecycle has something to exercise

All flagged `Test:TRUE`. Callable any time via `hub_test_seed()` to reset/recreate.

### 4. Notification safety
- **SMS:** already built and already defaults to routing everything to Brett's own phone (`TWILIO_TEST_MODE` default `TRUE`, `TWILIO_TEST_RECIPIENT` defaulting to `+14439617927`) — confirm this Config flag is actually `TRUE` on staging's Config sheet rather than rebuild it.

- **QuickBooks:** no change — stays fully stubbed in staging always, regardless of token used.
