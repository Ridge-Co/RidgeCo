**Why (Brett, Nov 2 14:06 and 14:22 ET).** Photos were "jammed" and the PDFs of recent inspections (back to 122 S Gilmor) were full of "Photo could not be loaded". Recipients needed the FULL-SIZE photo, from the ORIGINAL ("they need as much detail as possible"), links that never expire ("indefinitely"), reached from the report's own photo page. Also: move an issue to another area keeping all its info (a Basement issue on the Lyndale inspection was really Exterior Rear). And (14:32): the electrical panel section should read the panel's model info from the photo like the appliance label reader does.

**Root causes found.**
1. `fiPhotoView` read the whole `FI_Inspections` tab AND the whole `FI_Photos` tab from Google Sheets for EVERY image. A 139-photo report (Gilmor) = ~278 reads against the Hub-wide 60 reads/minute, so most images failed; the page replaced them with "Photo could not be loaded" and still printed. (PR #478 fixed only the UPLOAD side.) The live behaviour could not be observed (all 11 inspections are unpublished drafts, so `/fi/report` answers 403 to non-admins and `hub_prod_get` returns null for binary); this is established from the code, the read counts and #478's own measurements.
2. The phone shrank every photo to 1600 px / JPEG 0.82 BEFORE upload (`compressImage`), so the server never had the original: no link could have given "full size".
3. Thumbnails and "full size" were the same URL, and a saved PDF had only tiny non-clickable pictures.

**What changed.**
- **Photo viewing (worker.js).** `fiPhotoView` no longer touches Sheets: it asks `fiViewLookup`, a per-isolate lookup (report token -> that inspection's photos) filled by ONE pair of reads, shared by concurrent first requests (in-flight coalescing), refilled for free by `/fi/report`, aged out after 3 min, refreshed at most once per 15 s for an unknown photo, and an unknown token is remembered as unknown for 30 s (a scan cannot drain the quota). 30 views = 2 Sheets reads (was 60); 40 views at once = 2. A Drive 429/5xx is retried once. Cache header `private, max-age=86400`. A photo that just uploaded (standard or original) drops the cache so it is viewable at once. No expiring or signed URLs exist anywhere: the link is the report token and works as long as the report is published.
- **Originals (worker.js + phone).** `POST /fi/photo?kind=orig` stores the untouched file as `<photo>_original.<ext>` beside the copy in the inspection's Drive folder and records it on the SAME `FI_Photos` row in four new columns `Orig_Drive_File_ID, Orig_Mime, Orig_Bytes, Orig_At` (`ensureColumns` adds them to the live tab the first time, never `ensureTab`). Max 30 MB (`FI_MAX_ORIG_BYTES`; held twice in memory while sent to Drive = 60 of 128 MB). Refused loudly: standard copy not there yet (409 `photo_not_saved`), inspection not saved (409), empty (400), >30 MB (413), wrong type (415), Drive size mismatch (502), pointer not on the row after the write (500 `verify_failed`). Idempotent (`existing:true`). `GET /fi/photo/view?r=&p=&full=1` serves the original (`X-Photo-Variant: original`), falls back to the standard copy labelled `standard`; `&dl=1` downloads (`inspection-photo-<id>-original.jpg`). `/fi/report` adds `photo_full` = {photo id: original bytes} for photos that HAVE one, so pages never claim detail that is not there. Existing photos have NO original (the phone discarded it); they show as "Standard size".
- **Phone (`field-inspect.html`).** Still makes the 1600 px copy first (fast; what the report shows). The original file (or, for HEIC/other types or >30 MB, a FULL-pixel-size re-save at JPEG 0.95 then 0.88; a file that cannot fit is toasted and reported) is queued as its own row `<photo>__o` (kind `orig`) in the SAME IndexedDB store and the SAME #478 uploader: behind every standard copy, only after its own standard copy is on the server, same wait/backoff/status bar ("1 photo + 2 full-size copies waiting"), 240 s timeout (standard stays 75 s), blob freed once the server confirms. An original the server will never accept (over 30 MB) is toasted + reported to the failure log + dropped (no red bar that can never clear); a sign-in failure stays red with Retry. Removing a photo removes its queued original.
- **Report (`inspection-report.html`).** Thumbnails are links to the full-size photo (survive Print / Save as PDF); on screen a click opens the viewer with "Open full size" and "Download original". "View all photos (full size)" button, plus a print-only line with the gallery link. Failed images are retried 5 times (1.2 s, 2.4 s ...) before showing "could not be loaded"; printing now loads every photo first (screen view is lazy), shows "Loading photos... n of N", and if any are still missing it does NOT print by itself: it says how many and offers "Reload and try again" / "Print anyway".
- **Gallery (`inspection-photos.html`, new).** The report's photo page: `inspection-photos.html?r=<report token>`; same public gate as the report (403 `not_published` until published). Photos grouped by area, labelled by the issue/equipment they belong to, each with "Original - 4.2 MB" or "Standard size", "Open full size" and "Download". Same retry. Not in the `rc-related` group (public recipient page, no Hub nav, like `inspection-report.html`).
- **Move an issue (phone).** Issue editor, existing issues only: "Move to another area...". `moveIssueInDoc` moves the SAME issue object (same id, so roll-up, report and send marks keep working; every field incl. unsaved edits in the open editor, `wo`, `flag_send`, `sent`, `issue_type`). Its photos are added to the new area and leave the old one unless something staying behind still uses them. Target area cannot be excluded, full (60), the same area, or hold a duplicate id; any refusal changes nothing (dry run on a copy first). Goes through `mut()`, so autosave/offline/un-publish rules are unchanged. The confirmation offers "Go to <area>" and warns if the old area is now empty but still marked Poor/Fair (the condition is never changed silently). A moved-into "not inspected" area becomes "fair", as adding an issue by hand does.
- **Electrical panel.** New equipment kind `electrical_panel` (extra fields `amperage`, `spaces`) reads like the appliance label: `fiReadLabel` is told it is a panel, asked for brand / model-or-catalog number / amperage / spaces, not to take a single breaker's rating, and to say "unreadable" if only the handwritten door directory is visible; voltage/phase/max main go in notes. Aliases (breaker box, service panel, main panel, subpanel, load center, fuse box, electrical box) all become `electrical_panel`; dictation sorting knows the kind; the phone offers "+ Electrical panel" in any area named Electrical/Panel/Breaker and shows the two fields; the report prints "Amperage" and "Breaker spaces". The photo sent to the reader is the standard ~1600 px copy (same as appliances).

## Rule 236 (Oct 30 2026) — Field Inspection photos stuck on "waiting": Sheets read quota, auto-retry, visible status; Scheduler <-> Field Inspection links (BUILD_VERSION `2026-10-30.02-fi-photo-quota-nav`)
Brett (Oct 30, after tapping "Retry photos" twice): photos for several inspections stopped uploading; the first tap reduced the count, then it stuck. He asked to find the cause, make the system retry by itself (a wait is fine), show on the page whether to be patient or whether something is wrong, and link Field Inspection <-> the Scheduler (and make that the default for new related tools).
**Root cause (from tracing the code path and its read counts; the live Google quota state was not observed directly):** every `/fi/photo` request did 4 whole-tab Sheets reads (`FI_Inspections` twice, which holds up to 8 x 360 KB of report JSON per row, `FI_Photos` twice) plus ~7 more on a cold Worker instance (`fiEnsureTabs`), through `fiReadFresh`'s OWN raw fetch loop: 3 tries over ~2.4 s, invisible to the shared read meter, and its error text ("FI: Sheets read of … failed") was not recognised by `sheetsQuotaBusyError`. Google's limit is 60 reads/min/user shared by the whole Hub, so a batch of photos starved everything, the quota error surfaced as a generic 500 `internal` (a P1 telemetry row per photo), and the phone marked the photo failed or just sat there with no reason shown. The page also had no timeout (one hung request pinned the uploader) and no automatic retry beyond a 20 s poke.
**Fix, server:** `fiReadFresh` now goes through `sheetsRequest` (6-try ~15 s backoff, read meter, "Sheets API error on GET" text), after `invalidateTabCache(tab)` so it is still always fresh. `fiRoute` rethrows quota errors (`if (sheetsQuotaBusyError(e)) throw e;`) so the Worker's top-level handler returns the typed 429 `{busy:true, retry_after_seconds}` and ONE calm P2 `sheets_quota_busy` row; any other error is still a loud 500, and a failed telemetry write is now reported (`telemetry_error`, console) instead of swallowed. `fiPhotoUpload`: one lookup of the inspection per request via `fiFindInspectionForPhoto` (positive-only cache, 10 min, trimmed to ID/Active/folder, never caches a miss or a row with no folder), no `fiEnsureTabs` on every cold instance (lazy: only if a read says the tab/column is missing, and only when tabs were not already set up), and the write is verified by reading back ONLY the appended row (`updatedRange`), with the old full-tab check as fallback when Sheets does not say where it wrote. Result: warm photo = 2 reads (was 4 + up to 7), third photo of an inspection onward never reads `FI_Inspections`.
**Fix, page (`field-inspect.html`):** quota/network/server hiccups never mark a photo failed: it stays queued and the page retries by itself (server `retry_after` for quota; 5, 10, 20, 40, 60 s for other failures), 75 s request timeout, one-photo-at-a-time with a 0.9 s gap, `pumpPhotos()` honours the wait (the urgent-send loop that pokes it every 600 ms cannot bypass it; "Retry now" / coming back online can). Only a photo the server will never accept (too big / wrong type / not signed in) or one that failed 10 times in a row becomes "failed" (Retry photos button) and it is reported through `hubReportFailure`; busy for 6 rounds and the 4th failed try are reported too. The bottom bar says in plain words what is happening: "Uploading photo 2 of 5…", "Google is limiting how fast we can save (shared limit). Normal after a batch of photos — nothing is wrong. Retrying by itself in 23s", "Last try failed: <reason>. Retrying by itself in …", "offline — they upload by themselves when signal returns", or "N failed — <reason>".
**Navigation:** new shared `rc-related.js` + registry (`RC_RELATED`); `field-inspect.html` and `inspect.html` each show a chip linking to the other in the blue top bar; Field Inspection also added to the Scheduler's "Jump to…" menu. CLAUDE.md now says related tools join a group by default; `test/rc-related.test.mjs` fails on an unregistered or missing page. Photos only upload while `field-inspect.html` is open; leaving for the Scheduler triggers the browser's "leave site?" warning while photos are waiting.
**Not fixed / follow-ups:** `fiPhotoView` still does 2 full-tab reads per image view (a report with many images can burst the quota); `fiFolderOrganize` (limit 20, ~45 subrequests) is close to the 50 outbound-call ceiling; a failed `FI_Photos` append after a successful Drive upload can leave an orphan Drive file (the retry uploads again); an inspection trashed in the last 10 minutes still accepts photos from the cache.
**Silent-failure check:** no catch added that swallows; quota is a typed busy answer plus a calm P2 row and an on-screen countdown; every other failure is a loud 500 with telemetry (and a reported telemetry failure); the append is read back before `ok:true`; a photo that cannot upload ends as a visible, reported "failed" with a button.
**Verified:** new `test/fi-photo-quota.test.mjs` (30), `test/fi-photo-uploader-client.test.mjs` (26, real uploader code in a sandbox with fake network/timers), `test/rc-related.test.mjs` (18); `test/_fi-world.mjs` extended (whole-tab and one-row reads, append range); full suite 0 failing.
