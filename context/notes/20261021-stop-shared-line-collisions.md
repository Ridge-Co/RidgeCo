## FEATURE_LOG
**[FL-20261021-pr-collisions]** PR collision fixes (Oct 21 2026). **Regression rules:** (1) `BUILD_VERSION` in `worker.js` is a FROZEN base label; never edit it in a PR (the Branch policy guard fails a PR into main that does, unless the body has `allow-build-version-edit: true`). The version portals poll is `buildVersion(env).version` = base + `+` + deploy minute + `.` + first 8 chars of Cloudflare's version id, from the `[version_metadata]` binding `CF_VERSION_METADATA` in `wrangler.toml`; every deploy therefore gets a new version automatically. `GET /version` returns `{version, base, stamped, version_id, deployed_at}`. Unstamped (binding missing) is loud: `+unstamped`, a `warning` field, and one `build_version_unstamped` P2 ledger row per isolate. To confirm a deploy landed, compare `/version`'s `version_id`/`deployed_at` (or `base` for which code), not the literal in the source. Only `/version` and the selftest `version` use the stamp; the Read Meter, STR admin state and door-watchdog `build` fields still show the base. (2) A PR adds ONE file `context/notes/YYYYMMDD-<branch-slug>.md` (format in `context/notes/README.md`) and does NOT edit `CURRENT.md` / `FEATURE_LOG.md`; "load context first" now includes `context/notes/`; `scripts/doc_audit.py` counts each note as one entry. (3) A PR that is behind main but has no conflicts is brought up to date with the GH Broker tool `update_pull_request_branch`, not re-cut; re-cut only when it is genuinely conflicting. Tests: `test/build-version-stamp.test.mjs`, `test/guard-check.test.mjs`.
