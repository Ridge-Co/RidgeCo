"Re-uploading the photos for the previous inspections is a major setback. Workaround?" (Note: the Drive copy is the 1600 px copy, not the original; the phone never uploaded originals before #480.)

**What changed (`field-inspect.html`, phone only; no worker change, the server already accepts `POST /fi/photo?kind=orig` for any saved photo).**
- Review screen: new card "Full-size photos" -> "Attach full-size originals…". It asks the server (`/fi/report`, admin) which photos in this inspection have NO original (`photo_full`), minus any original already uploading from this phone, and says how many.
- Brett chooses the gallery pictures (any number, any order, extras from other jobs are fine). The page reads each stored copy (via the report photo route) and each pick, fingerprints both (16x16 brightness-comparison hash = 256 bits, same two-step downscale for both) and matches them. A pair is attached ONLY if it is the best match in both directions, within 48 bits, and at least 16 bits clearer than the runner-up on both sides; certain pairs are taken out and matching repeats (settles picks that were only unsure because of them). Near-identical shots (same picture to a fingerprint) are LEFT ALONE and listed by file name, never guessed.
- Matches are queued as rows `<photo>__o` (kind `orig`, `late:true` = no local standard copy needed), fed in at most 6 at a time (each is several MB), through the same uploader (retry/wait/status bar).
- Result sheet: matched count, not-sure list, pictures that matched nothing, unreadable pictures (with reason), stored photos that could not be loaded (also reported to the Hub failure ledger), originals that could not be kept, photos still without an original, "Choose more photos".
- Photo viewer: "Attach full-size original…" for ONE photo (no matching) for any leftover.
- **Uploader fix (also helps normal photos):** `pumpPhotos` works from a snapshot of the queue, so rows queued while a pass was running were forgotten until something else poked it (found by the end-to-end run: 7 of 13 uploaded then stalled). A poke during a pass now sets `S.pumpAgain` and a follow-up pass runs when it ends. `queueOriginal(rec, id, file, opts)` returns true/false.

**Tests.** New `test/fi-match-originals.test.mjs` (47): fingerprints from REAL Chromium (`test/fixtures/fi-match-hashes.json`, 94 natural pictures, original vs the page's own 1600 px/0.82 copy): same picture <= 8 of 256 bits, unrelated >= 69; 400 random inspections, ~7,000 attachments, ZERO to a wrong photo; flow, failure listing, throttle, late rows, pump-again, UI hooks. Real-browser end to end `test/manual-verify-fi-match-originals.mjs` (`OM_IMG_DIR=<jpgs>`; real page + real worker FI code): 13 of 13 originals on their own photo byte for byte, 0 wrong, the two identical pictures left alone and listed, 21 pictures from "other jobs" ignored, single-photo button works. Full suite 304/304.
**NOT verified:** real Samsung gallery originals (HEIC/odd EXIF, very dark indoor shots) against real stored copies; a multi-MB upload over cellular for 40+ photos; Android file-picker behaviour with 100+ selected files; the pictures in the test were natural photos resized to 4032x3024, not phone-camera files. Matching is conservative: anything doubtful is left for "Choose more photos" or the single-photo button.
**Known gaps.** Two pictures that differ only in brightness fingerprint identically and are always left for the single-photo button. "Before you publish" blocks while originals are still uploading (by design: published links should carry the full-size photo).

## FEATURE_LOG
**[FL-20261102-fi-match-originals]** (1) Never attach an original to a photo on a guess: the matcher requires a mutual best match within 48 bits with a 16-bit gap on both sides; do not loosen `OM_MAX_DIST`/`OM_MARGIN` without re-running `test/fi-match-originals.test.mjs` and the real-browser fixture (unrelated pictures were >= 69 bits apart, the same picture <= 8). (2) Anything the matcher does not attach is LISTED (not sure / matched nothing / unreadable / could not load / could not keep), never skipped silently. (3) A queued original of an earlier photo is a `late` row: the uploader must send it without a local standard row (a normal original whose photo is gone is still dropped). (4) `pumpPhotos` must never forget rows queued while a pass is running (`S.pumpAgain`). (5) Originals are fed to the phone queue at most `OM_QUEUE_AHEAD` (6) at a time.
**Silent-failure check:** no catch swallows; every failure (report lookup, stored photo load, unreadable pick, queue failure, unsure/unmatched) is shown in the result sheet and the Hub-side ones go to the failure ledger via `reportPhoto`; uploads reuse the existing verified, retried, visible uploader.
