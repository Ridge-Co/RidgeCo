GitHub /pulls/N -> HTTP 401]`, count 82, notified 80 times) and F-c1795030305235-0 (P0, `scheduler:queue_sync` overdue). `hub_impr_daily` (07:30 ET) and `hub_impr_thu` also failed today with the same text because they run the same sync step.

**What happened.** The Hub sends `GITHUB_READ_TOKEN` to GitHub as an optional extra (the repo is public, anonymous reads work). Until Nov 18 18:32Z GitHub answered 403 (rate limit, already treated as calm). From the 18:47Z tick it answered 401 on every call. A 401 can only come back when a token IS sent and GitHub refuses it (anonymous calls never get 401). The code only softened 403/429, so every 401 became a job error: `queue_sync` stayed red for 17+ hours, the P0 re-fired every 15 minutes, and the daily and Thursday improvement jobs went red too. Brett rotated the token on Nov 18; the error continued, because the value the production Worker holds is still not accepted by GitHub (still failing at 14:02Z Nov 19, including a PR opened after the rotation).

**Fix (`worker.js`, `ghPublicJson` + `opsQueueSync`).**
- `ghPublicJson`: on 401 with a token, remember the refused token for 10 minutes (per isolate), ask GitHub again WITHOUT it (public repo), and carry on. A token with a space, line break or odd character inside is not sent at all (fetch would throw) and is treated the same way. All six callers (queue sync, stage check, risk check, improvements sweep, ...) get this.
- `opsQueueSync`: files ONE calm P2 `github_read_token_rejected` (never P0) that names GitHub's own words, and what the Worker actually holds: token kind (classic / fine-grained / unrecognised), length, an 8-hex one-way fingerprint, and usual paste mistakes (quote marks, a `Bearer ` prefix, spaces or line breaks). The token value is never written anywhere. If the row cannot be filed, that is a job error.
- Everything else stays loud: a 401 with NO token sent, a 500, and a 403/429 after the retry are handled exactly as before.
- The fingerprint is how a rotation that did not take effect shows up: set the secret again, and if the fingerprint in the row does not change, the new value never reached this Worker.

Tests: new `test/queue-sync-github-401.test.mjs` (38 checks, real `ghPublicJson` / `githubTokenShape` / `opsQueueSync` source with a fake fetch, Sheets and ledger): refused token, retry without it, 10-minute skip, re-try after 10 minutes, a different token tried at once, the whole pass still moves all rows, exactly one P2 and no job error, the 400-character ledger cap, the token value never in the ledger, happy path reports nothing, 401-then-403 gives both calm rows, 401 with no token and a 500 stay loud, a line-break token is not sent, an unfileable report is a job error, token-shape cases, source guards. Harnesses of `queue-sync-github-403`, `ops-queue-upgrade` and `queue-v2` now define `_ghTok` (and extract the new helpers).

## FEATURE_LOG
**[FL-20261119-github-token-401]** Regression rules: (1) a GitHub 401 while a token was sent never fails a scheduler job: drop the token, retry once anonymously, file ONE P2 `github_read_token_rejected`; a 401 with no token sent stays a job error. (2) The token value, or any part of it, never goes into the ledger, a response or a log; only kind, length, a one-way 8-hex fingerprint and paste-mistake flags. (3) The ledger caps a message at 400 characters, so the diagnosis comes first and the fix last. (4) A rejected token is skipped for 10 minutes per isolate and tried again after, so a re-set secret is picked up.
