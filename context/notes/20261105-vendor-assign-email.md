# Vendor "new work order" email (Nov 5 2026) — PR into main, head `feat/vendor-assign-email`, merged: no
## CURRENT
**Why (Brett, Nov 5 18:21):** "Send them an email when assigned. Just something basic with a link to the work order, which would be on their portal. Period. That will just give us one more point of contact for them." Before this a vendor assignment sent ONLY a text (portal link) and the tenant text; the only vendor email was the invoice-received confirmation.
**Built:** `assignVendor` now also emails the vendor right after the vendor text, so every path that assigns (Assign modal, New Work Order, Duplicate, recurring) gets it. The email is basic: "Hi <first name>, you have been assigned a new job: WO <id> (<trade>) at <address>. Log in to your vendor portal to accept or decline:" plus a "View work order" button. English, or Spanish for a Spanish-language vendor. Link = `vendorPortalLink` (PIN login to vendor.html), never the no-login share link. NO lockbox code and NO tenant contact (they unlock in the portal after Accept).
**Gates (an email has no test-number redirect, so these are stricter than the text):** sent only when Config `TWILIO_ENABLED` = TRUE AND `TWILIO_TEST_MODE` = FALSE (default is Test Mode ON = no email to real vendors), the vendor's `SMS_Enabled` is not FALSE, the property's "Texts to vendors" switch is not FALSE, and the vendor has a valid email. `notify:false` assignments send nothing. A vendor's STOP text opt-out does NOT block the email (it is a text rule). A repeat Assign to the SAME vendor whose email already went is not emailed again (new Work_Orders column `Vendor_Email_Sent`, created by `ensureColumns`).
**Never silent:** `assignVendor`'s response carries `vendor_email_detail` {status sent | skipped | failed, reason}. No email on file or a gate closed = `skipped` with the reason in words. A malformed address, a Gmail failure, or an unreadable Config = `failed` AND reported to the failure ledger (`vendor_assign_email`, P2/P3). Every real attempt is written to the work order's communication audit (channel email, type `vendor_job_assigned`); a failed audit write is itself reported. The email can never fail the assignment.
**Tests:** `test/vendor-assign-email.test.mjs` 42 checks (real functions against fakes: every gate, content + Spanish + escaping + no access info, sent / skipped / failed / staged, ledger-and-audit-both-down, wiring in assignVendor). Whole suite green locally. Staging: `gmailSendEmail` is stubbed there, so staging proves the wiring and the `vendor_email_detail` field, not a real delivery.
**NOT verified / open:** no real email has been sent. The first real one goes out when Brett turns Test Mode OFF (or the first live assignment after it is off) to a vendor with an email on file; check the vendor's inbox and the WO audit trail then. The UI does not yet show `vendor_email_detail` (the text's detail is not shown in the UI either); failures reach "Needs your attention" through the failure ledger.
