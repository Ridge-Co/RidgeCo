# STR bulk send: a verification re-read that cannot be done is "saved, not confirmed", never "FAILED" (Oct 29, 2026)
Build 2026-10-29.02-str-verify-soft. Branch fix/str-verify-soft-oct29. Queue item 228. (Proposed FEATURE_LOG rule 237; renumber at merge if it collides.) Risk class: MEDIUM-SAFE (cleaning scheduler admin swap; no QuickBooks, no money, no auth; it can only delay or withhold a cleaner text, never add one).

## Trigger
`strBatchSet` / `strAddRows` write, then re-read the tab to prove the write landed. On a big swap the shared Sheets READ quota ran out on that re-read, the error threw into `strStageSheets`, and every date was marked FAILED ("Sheets API error ... Quota exceeded") although the rows were saved. Brett saw "It did NOT go through" for a swap that had gone through, and nobody was texted.

## Rules (do not break)
1. `strBatchSet(env, tab, updates, {soft:true})`, `strAddRows(env, tab, list, {soft:true})` and `strMarkBatch(ctx, changes, {soft:true})` are OPT-IN. Without `soft` every caller behaves exactly as before (the re-read error throws). With `soft`, a failed re-read AFTER the write went in returns the ids as `unverified` (`out.unverified` / `ids.unverified` / `res.unverified`), not ok and not failed. Only the swap's `strStageSheets` passes `soft`.
2. An unconfirmed turnover/mark item stays `pending` (with `unv` = the reason). The `sheets` stage returns "not finished", so the audit, calendar, text queue, send and email stages DO NOT RUN. The next resume re-reads STR_Turnovers and closes the item through the existing "already has this one" branch (or re-writes it if the write had not landed). Texts are still queued only for `status === 'done'` items (`strOkItems`).
3. Spacing: each later pass first waits STR_UNV_GAP_MS (10 s) since the last pass (Google's quota is per minute), up to STR_UNV_MAX (5) passes. These passes are not "tries": the driver's 3-try cap still counts real errors only.
4. Out of tries: the item becomes status `unverified` (never `failed`), with a `save_unverified` error naming the date ("saved but NOT confirmed ... Refresh and check before doing it again. No text was sent for it."). The change finishes as `partial` (counts.unverified), Brett gets the normal telemetry row + alert, the audit row is `admin_swap_unverified` / `admin_mark_unverified`, the page pill says SAVED - NOT CONFIRMED. No text, calendar write or invite is made for an unconfirmed date. The driver's 3-try throw cap uses the same give-up (an unconfirmed item is never relabelled FAILED).
5. Backup marks (swap path): an unconfirmed mark sets `mku` on the item and holds the stage the same way; the assignment itself is already verified done. If the mark can never be confirmed: loud `backup_mark` error, and the displaced cleaner's `back` text is NOT queued ("Tell them yourself" warning). Marks and closed offers are settled once per item (`mk`, `oc`), so a later pass does not redo them.
6. Unchanged on purpose: a write that did not land (re-read works, value differs) is still FAILED; a POST error is still FAILED; any failure AFTER a text is queued or sent stays loud (text_failed error naming the cleaner, telemetry, alert to Brett). `guardAppendedIds` (reads only when the append response is surprising) still throws `write_not_landed`.

## Known limits
Any re-read error (not only the quota) is treated as "cannot confirm", because the write already went in. A waiting offer that was closed but could not be read back is a warning on the result, not an error (no text depends on it). The sheets stage can now take up to about 40 s of waiting across passes on a stuck quota; the page keeps resuming by itself (it allows 40 passes). If the Hub cannot even load the tabs for the next pass (the same quota), the page shows its existing Continue button and the saved job waits; nothing is texted meanwhile.
